# 第 N 期 PRD 模板（Product Requirements Document）

> **这份模板给谁用**：Starsky（产品一号位）在每期正式开 spec 之前写。
>
> **写多长**：目标 **2-3 页**。我们是 3 人团队，不是大厂——别模仿大厂 30 页 PRD 那套。
>
> **用户故事精髓**：不是写代码怎么做，是写"**一个具体用户，在什么场景下，想解决什么问题**"。
>
> **写完之后**：作为 `docs/spec-vN.md` 的输入。Spec 讨论阶段可以随时回头对照 PRD。

---

## 2. 用户故事（做什么）

> 格式：**作为[用户]，我想[做什么]，这样我就能[获得什么]**。
>
> 优先级三档：P0 必做 / P1 重要 / P2 有则更好。不允许全 P0——那等于没排序。

### 故事 1（P0）

**作为** 骑完 100km 的小明
**我想** 打开 App 就看到"刚才那趟骑行破了你 3 个个人纪录"
**这样我就能** 感到激动、截图发朋友圈、明天还想出去骑

- [ ] 小明首页能看到红点提示

- [ ] 每条能跳到对应赛段详情页

## 3. 本期明确**不做**（边界）

> 防 scope creep 的关键。列出"看起来应该做、但本期故意不做"的事。

- ❌ 微信服务消息推送 → 留到第 N+1 期（理由：需要模板消息资质）
- ❌ 多运动支持（跑步/徒步）→ 留到用户量到 100+（理由：垂直定位）
- ❌ ...

---

## 4. 成功标准（怎么算本期有价值）

> 不是"代码上线"——那是技术指标。
> 是"**这期做完对用户和产品有什么可验证的影响**"。

**可量化**：
- 本期上线 2 周后，用户平均每日打开 App 次数从 X 提升到 Y
- Strava 自动同步用户占比达到 Z%

**可感知**（没数据也能判断）：
- 小明和 CCF 用起来觉得"这 App 开始有内味了"
- 朋友圈出现至少 3 次自发截图分享

## 7. 风险与缓解（产品视角）

> 不是技术风险（那些 spec 会写）。是**产品视角**的风险：用户会不会不买账、时间来不来得及、商业模型会不会崩。

| 风险 | 缓解 |
|------|------|
| 只有 2 个真实用户，反馈样本太小 | 做完后拉 CCF、颜颜、太原骑友群先内测 |
| Strava 绑定流程 4 步跳转，流失率可能高 | H5 页面写清楚"为啥要 4 步"，降低疑惑 |
