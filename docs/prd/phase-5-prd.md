> **本文件性质**：v5 期**战术 PRD**，给执行 spec subagent 看的执行手册。
>
> **写作规范**（Tim 2026-04-28 拍）：每个子任务严格 **9 章节**（用户目标 / 使用场景 / 功能范围 / 用户流程 / 页面&状态 / 数据需求 / 异常情况 / 验收标准 / 不做项）+ 来源追溯一行。

## 0. v5 期 north star（顶层概览）

**4 主轴并列全做**（**禁止 spec subagent 自降优先级**）：

- **B 主轴 - 赛段内容层**：让赛段从"GPS 线段"变"有内容的地方"
- **C 主轴 - 数据成长层**：让用户在 velo 上看见自己的进步
- **A 主轴 - 个人主页层**：用数据驱动方式呈现身份感（Strava 风非 Letterboxd 4 最爱）
- **D 主轴 - 管理员工具层**：让团队（Tim + 颜颜 + CCF + 各城贡献者，规模 v5 期 15-20 位骨干）能高效协同维护赛段库

**1 个跨主轴软目标**：上传 GPX 后处理性能 ≥ 90% < 5 分钟（10 分钟 timeout 兜底，参 §7）。

**预估工期**：8-10 周（三人并行折算）。
**前置依赖**：Sprint 0 必先清完 5 项 P1 tech-debt（参 §2）。

## 3. B 主轴 - 赛段内容层

主轴定位：让赛段从"GPS 线段"变成"有内容的地方"。底色 **C → A → B**（数据驱动 / 排行榜硬核 / 适量活人感介绍 —— Q3）。

### 3.1 子任务 5.B.1 - 坡度剖面 + 难度评级 + 城市标签

**用户目标**：骑手骑前一眼判断"这条赛段难不难、会不会被拉爆"——不用懂技术词。

**使用场景**：约骑前夜，在 velo 搜某条赛段（如"龙井-虎跑环线"），点进详情页第一屏判断要不要去 / 要不要找队友带。

**功能范围**：
- 赛段详情页第一屏 = 海拔曲线 + 难度评级 badge + 城市 tag + 基础数字（距离 / 爬升 / 最大坡度 / 平均坡度）
- 海拔曲线沿用 v4 Activity 详情页同款形态（**不加色块 / 3D / 花哨**——Tim 砍 2026-04-28）
- 难度 **4 档**（极难 / 难 / 中 / 易），各档定性偏好（具体阈值算法 spec 决定）：
  - 极难 ≈ "90% 普通骑手走着上山" / 难 ≈ "FTP 200W 以下会被拉爆" / 中 ≈ "中级有挑战" / 易 ≈ "新手友好"
- 城市枚举 **6 城**（北/上/杭/深/成/太）+ unknown
- 220 条现有赛段全部回填难度 + 城市
- 赛段列表支持 city + difficulty 筛选

**用户流程**：
1. explore 页搜或选赛段 → 点进详情页
2. 第一屏看到海拔曲线 + 难度 + 城市 + 数字
3. 列表页可按 city / difficulty 筛

**页面/状态**：
- 赛段详情页（v4 现有，加新组件）：加载中 / 数据完整 / city='unknown'（显示"未知"tag）
- 赛段列表页（v4 现有 explore）：加筛选器 / 无匹配显示空状态

**数据需求**：
- 每赛段需有：难度（4 档）+ 最大坡度 + 城市归属
- 海拔曲线沿用现有 elevation_profile（80 点采样，**不动数据格式**）
- segments 表加 3 字段（difficulty / max_gradient / city）—— **防火墙破例 3 处**，必须在 segments 加，不允许新表

**异常情况**：
- 老数据 city 推断失败（GPS 起点跨城）→ 填 'unknown'，5.D.3 团队人工修正
- max_gradient 单条计算失败 → 记 logger 跳过，不阻塞迁移整体
- 用户筛 difficulty + city 无匹配 → 空状态"该城市暂无此难度赛段"

**验收标准**：
- 任意赛段详情页第一屏看到海拔 + 难度 + 城市 + 数字
- 220 条现有赛段全部有难度 + 城市（city='unknown' 占比 < 30%）
- 列表筛 city + difficulty 结果正确

**不做项**：
- ❌ 实时坡度提醒（INV-P03）
- ❌ 用户自定义难度阈值（v6+）
- ❌ 海拔 3D 可视化（v7+）
- ❌ 坡度色块叠加 / 红橙绿色阶（Tim 砍 2026-04-28："完全没用"）

**来源**：Q3 + product-spec §3.2 + Tim 砍色块（2026-04-28）

### 3.2 子任务 5.B.2 - AI 介绍 30-50 精选（RAG 留接口不实现）

**用户目标**：精选赛段（30-50 条）有"活人感介绍"——像本地骑友写的避雷 / 氛围描述（"路面晒得像火""逆天陡坡爬完腿发抖"），帮骑手心理预判。

**使用场景**：骑手在赛段详情页看完基础信息往下翻，在精选赛段看到一段 70 字的活人感介绍；普通赛段 description 区域空白。

**功能范围**：
- AI 介绍**只覆盖 30-50 精选**赛段，普通赛段 description 空着
- 单条 50-100 字（AI 输出目标 / admin 编辑无硬限 / 见上方 2026-05-06 修订）/ 1-2 个细节 / 不堆砌（满足 RUBRIC-CONTENT 至少 3/4 条）
- AI 是**运营工具**（团队批量生成草稿，5.D.2 人工审核改写后入库）—— **不是用户实时看到 AI 生成**
- RAG **留接口不实现**：建 `app/agent/` 独立目录预留架构，v5 不上向量检索
- AI 直连 Anthropic Claude API，**不上向量检索 / 不建 agent_rag_chunks 表**

**用户流程**：
1. 用户进入赛段详情页
2. 普通赛段：description 空白或"暂无介绍"
3. 精选赛段：description 显示活人感介绍（人工审核改写过）
4. 用户感知不到 AI（语言活生生像本地骑友）

**页面/状态**：
- 赛段详情页 description 区域
  - 精选赛段：显示活人感文本
  - 普通赛段：空白或"暂无介绍"

**数据需求**：
- 每条精选赛段需有：AI 草稿 + 团队改写版 + 审核状态
- segments.description 字段已有（v0），不动结构
- 新建 segment_ai_drafts 表存草稿 + 改写版 + 状态（防火墙原则）

**异常情况**：
- Anthropic API 限流 / 失败 → 记 logger，不打断业务流，事后重试
- 草稿质量低于预期 → 走 5.D.2 人工改写流程
- 30-50 精选选择口径漂移 → 候选池审核（5.D.1）锁住

**验收标准**：
- 30-50 条精选赛段在详情页显示活人感介绍
- 普通赛段（170-190 条）description 空白
- 用户感知不到 AI（语言像本地骑友）

**不做项**：
- ❌ 用户实时触发 AI 生成介绍（D-P07）
- ❌ RAG 向量检索 / agent_rag_chunks 表（v5 留接口）
- ❌ 全部 220 条赛段都喂 AI 草稿（违反 30-50 边界）

**来源**：Q4 + Q5 + Tim 拍 RAG 留接口 + product-spec §3.2 + RUBRIC-CONTENT §6

### 3.3 子任务 5.B.3 - 赛段搜索

**用户目标**：让骑手快速找到记得名字的赛段（"我想找龙井那条环线"），不用滚长列表。

**使用场景**：骑手在 explore 页有具体赛段名想找——直接搜，不用筛 city / difficulty。

**功能范围**：
- explore 页顶部加搜索栏 —— 输入即搜索
- 中文模糊匹配（"龙井" 能匹配 "龙井-虎跑环线"）
- 搜索 + 现有 city / difficulty 筛选可同时使用（AND）
- 用 SQL LIKE 实现（**不装 PostgreSQL 中文全文搜索扩展** —— Q问题 2b："工作量小隐患低"）

**用户流程**：
1. 骑手在 explore 顶部搜索栏输入关键字（≥ 2 字符）
2. 下拉显示匹配赛段列表
3. 选中跳转赛段详情页
4. 可同时配 city / difficulty 筛

**页面/状态**：
- explore 页搜索栏
  - 输入中（loading）
  - 有结果（列表）
  - 无结果（空状态）
  - 空输入（显示所有赛段）

**数据需求**：
- 沿用 segments 表 name 字段（不动）
- 中文 LIKE 不区分大小写（PostgreSQL ILIKE）

**异常情况**：
- SQL 注入风险 → ORM 参数化（必须 SQLAlchemy ORM，禁止 f-string 拼 SQL）
- 输入特殊字符（%、_）→ ORM 自动转义
- 搜索 + city/difficulty 同时无匹配 → 空状态

**验收标准**：
- 输入"龙井"返回包含"龙井"的赛段列表
- 中文不区分大小写
- 空搜索返回所有赛段
- 搜索 + city/difficulty 同时使用结果正确

**不做项**：
- ❌ 全文搜索引擎（v5 LIKE 够，v7+ 千级再考虑）
- ❌ 搜索历史 / 智能联想 / 拼写纠错（v6+）

**来源**：Tim 问题 2b

## 4. C 主轴 - 数据成长层

主轴定位：让用户在 velo 上看见自己的进步——三种被看见的路径全做（Q6 D：即时反馈 + 主动查询 + 被动推送）。

### 4.1 子任务 5.C.1 - 即时反馈

**用户目标**：骑手骑完上传 GPX 后，赛段页**秒级看到对比反馈**（"比上次快 25 秒"）—— 即时验证今天怎么样。

**使用场景**：骑手骑完赛段，回家或途中上传 GPX，立刻打开 velo 看赛段详情页 → 屏幕直接显示对比，不用刷新 / 不用等通知。

**功能范围**：
- 赛段详情页"我的成绩"区域显示 3 个数：这次时间 / 上次时间 / PR
- 这次破 PR 时显示 PB 标记
- 首次骑某赛段：显示某种"首次"状态（具体文案 spec 决定）
- 沿用 segment_efforts 表 + 现有索引（**不允许新建对比缓存表**）

**用户流程**：
1. 骑手骑完上传 GPX
2. 后台处理完后（参 §7 worker 5min 门槛）
3. 用户点开赛段详情页
4. "我的成绩"区域秒级显示：这次 / 上次 / PR + PB 标记（如破）

**页面/状态**：
- 赛段详情页"我的成绩"区域
  - 首次完成（无对比）
  - 第二次起（vs 上次）
  - 破 PR（PB 标记）
  - 没破 PR（距 PR 差距）
- activity 还在 processing → 显示"处理中"

**数据需求**：
- 沿用现有 segment_efforts 表 + idx_efforts_segment_user_time 索引
- 不动数据结构

**异常情况**：
- activity 还在 processing → "我的成绩"显示"处理中，请稍后"
- activity failed → 显示失败状态，引导重试
- 首次骑无对比 → 显示"首次完成"
- segment_efforts 查询超时 → fallback 显示纯成绩数字（无对比）

**验收标准**：
- 用户首次骑：UI 显示"首次"状态
- 第二次起：显示 vs 上次对比
- 破 PR：显示 PB 标记
- 没破：显示距 PR 差距

**不做项**：
- ❌ 自动分享朋友圈（v6+ 关注体系）
- ❌ 对比赛友（v6+ 关注体系）

**来源**：Q6 路径 A + product-spec §3.2

### 4.2 子任务 5.C.2 - 主动查询：功率曲线 + 月年对比

**用户目标**：骑手主动打开个人页 → 二级页看自己的"功率曲线" + 月 / 年对比 → 看到长期成长轨迹。

**使用场景**：骑手某天闲着想看自己最近练得怎样 / 跟去年比有没有进步 → 打开 velo 个人页点"功率曲线"卡片 → 进二级页看曲线。

**功能范围**：
- 个人页加"功率曲线"卡片入口
- 二级页展示：时长分桶曲线（X 时长 / Y 瓦特）+ 多 period 叠加
- 时长 buckets 数量 spec 决定（**建议参 Strava 行业标准 1s/5s/30s/1min/5min/20min 6 档**）
- period 切换：本月 / 上月 / 本年 / 上年（4 档至少，all_time 可加）
- FTP 为空用户仍可看（绝对瓦数，不规范化）
- 用现有 trackpoints.power 字段（**不允许加新功率字段到 activities 表**）

**用户流程**：
1. 用户进入个人页
2. 点"功率曲线"卡片
3. 进入二级页看曲线
4. 切换 period 看对比

**页面/状态**：
- 个人页（v4 现有）：加"功率曲线"卡片入口
- 功率曲线二级页（新页面）
  - 加载中
  - 数据完整（多曲线叠加）
  - 数据不足（< 1 周）→ 显示"骑车 1 周后看"
  - period 切换中

**数据需求**：
- 沿用现有 trackpoints.power 字段（已存）
- 计算结果建议缓存（spec 决定具体策略，建议 Redis）

**异常情况**：
- 用户无任何 activity → 空状态"上传第一次骑行后看"
- period 切换数据计算超时 → 显示加载提示，不打断
- FTP 为空 → 显示绝对瓦数，UI 不展示规范化指标

**验收标准**：
- 用户从个人页进入功率曲线二级页
- 多 period 曲线叠加渲染正确
- FTP 为空用户能看绝对瓦数
- 切 period 顺畅（< 3 秒响应）

**不做项**:
- ❌ CTL/ATL/TSB 训练负荷（Strava Premium 风，违反 INV-P04 / D-P03）
- ❌ 心率曲线（v5 P0 没列，v6+）
- ❌ 跟其他用户对比功率（v6+ 关注体系）

**来源**：Q6 路径 B + product-spec §3.2

### 4.3 子任务 5.C.3 - 被动推送：进步检测器

**用户目标**：骑手不主动查也能被推通知"你进步了"——比如 5min 功率涨 5W 自动推。

**使用场景**：骑手骑完上传后约 1 分钟，velo 检测到进步阈值 → 推通知 → 用户不主动查也能感受到自己变强。

**功能范围**：
- 系统检测进步阈值 → 主动推通知（沿用 v3 通知列表 + 红点）
- 进步类型 3 种：5min 功率进步 / 赛段 PB / 月度总结（每月 1 日）
- 进步阈值 **5W**（5min 最大平均功率涨 ≥ 5W —— Q6 路径 C Tim 拍）
- 通知点击进入"成长详情页"（曲线对比图）
- 通知系统沿用 v3 detector.py 同模式（PR/KOM 检测器扩展）—— **不允许新建独立检测系统**
- 推送方式 v5 沿用通知中心 + 红点（**不上微信服务消息** —— P2 tech-debt）
- 用户可在 settings 关闭进步推送（沿用 v4 mute_notifications 字段）

**用户流程**：
1. 骑手骑完上传 GPX
2. 后台处理完成 + 进步检测器检查
3. 检测到进步 → 写 notification 表
4. 用户在通知中心看到红点 + 通知文案
5. 点击通知进入成长详情页

**页面/状态**：
- 通知中心（v3/v4 现有）：加新 type 3 种
- 成长详情页（v5 新页面）：曲线对比图

**数据需求**：
- 沿用现有 notifications 表（type + payload 字段已支持）
- 进步阈值数据用现有 trackpoints.power

**异常情况**：
- 进步检测算法异常 → 该 activity 不推送，记 logger
- 通知发送失败 → 表保留，下次列表加载补显示
- 用户开启 mute → 不推送
- 退步推不推 → spec 决定（PRD 不预设）

**验收标准**：
- 用户上传 activity 后检测到进步 → 1 分钟内推通知
- 通知点击进入对比详情页
- 进步推送跟 5.C.1 即时反馈不重复
- 用户能在 settings 关闭进步推送

**不做项**:
- ❌ 微信服务消息推送（P2 tech-debt）
- ❌ 比较其他用户的进步推送（v6+ 关注体系）

**来源**：Q6 路径 C（5W 阈值 Tim 拍）+ v3 detector 同模式

## 5. A 主轴 - 个人主页层

主轴定位：用数据驱动方式（Strava 风非 Letterboxd）呈现身份感。**4 最爱赛段已砍**（Q7：Tim 拍"数据是基础，没数据谈不上社交"，推迟 v6+）。v5 期 2 子任务：个人骑行热图 + 看他人主页（只读）。

### 5.1 子任务 5.A.1 - 个人骑行热图（按城市切）

**用户目标**：骑手打开个人页看自己的"骑行热图"——本城市常骑路段一目了然，激发"下次去 X 路骑骑"。

**使用场景**：骑手某天闲着刷小红书无聊 → 打开 velo 个人页看热图 → 看到这个月在主城市主要骑了哪些路段，没去哪 → "下月去新地方"。

**功能范围**：
- 个人页加热图组件 —— 默认显示主城市
- 城市切换 segment-control —— 切换任意 6 城（北/上/杭/深/成/太）
- 用户去过的城市才显示选项
- 用微信小程序 map 组件 + heatmap 图层
- 用户主城市推断：首次上传 GPX 自动填，settings 可手动改

**用户流程**：
1. 用户进入个人页
2. 看到"我的 [主城市] 热图"
3. 点城市切换 → 切到其他城市
4. settings 可手动改主城市

**页面/状态**：
- 个人页（v4 现有，加热图组件）
  - 主城市未填（新用户上传前）→ 显示"上传第一次骑行后看"
  - 主城市已填，本城市无骑行 → 显示空热图
  - 切换城市 → 加载中 → 该城市轨迹叠加
- settings 页（v4 现有）：加"主城市"字段编辑

**数据需求**：
- 沿用现有 simplified_track JSONB + Trackpoint.geom PostGIS POINT
- users 表加 city VARCHAR(32) NULL —— **防火墙破例 1 处**，必须在 users 加，**不允许新建 user_metadata 附属表**
- 老数据回填策略 fallback 链：近 30 天 most-frequent → 全部 activities most-frequent → NULL

**异常情况**：
- 新用户无 activity → city = NULL，显示"上传第一次骑行后看"
- 主城市推断失败（GPS 跨城）→ fallback 链最终 NULL 时空状态
- 切到没骑过的城市 → 显示空热图"在 X 城还没骑过"
- 大量 trackpoints 渲染卡顿 → 后端聚合 + 前端按缩放级别加载（spec 决定具体策略）

**验收标准**:
- 首次上传 GPX 后 user.city 自动填
- 个人页热图默认显示主城市
- 切换其他城市，只显示该城市轨迹叠加
- settings 能手动改主城市

**不做项**:
- ❌ 跨城热图聚合（违反"按城市切"）
- ❌ 时间维度切片（近 1 月 / 3 月 / 全部，v6+）
- ❌ 看其他用户的热图（D-P08 隐私默认谨慎）

**来源**：Q7 + Tim 砍 4 最爱 + product-spec §3.2

## 6. D 主轴 - 管理员工具层

### 6.1 子任务 5.D.1 - 候选池审核

**功能范围**：

- 团队人工勾选最终 **30-50 条 / 每城 5-8 条**（Q5 拍）—— 不允许偏离比例
- 候选池脚本必须**幂等**（重跑不重复写入）
- 选中赛段触发 5.B.2 AI 写草稿
- 防火墙：新建 segment_curation_pool 表（不动 segments 表）

**用户流程**：
1. 脚本周期性跑 → 生成候选池 100 条
2. 团队成员（is_admin）登录 H5 admin → curation-pool 页
3. 看候选列表 + 当前选中数（"5/50"）
4. 勾选某条 → 触发 AI 写草稿 + 更新计数

**页面/状态**：
- H5 admin curation-pool 页（新）
  - 加载中
  - 候选列表 + 当前选中数
  - 选中超 50 → 前端阻止
  - 选中数 < 30 → 提示"还差 X 条"

**数据需求**：
- 新建 segment_curation_pool 表（含 segment_id + pool_score + selected + 选中人 + 时间）
- 防火墙：不动 segments 表

**异常情况**：
- 脚本跑失败 → 记 logger，不影响线上
- 团队选中数超 50 → 前端阻止 + 提示
- 选中触发 AI 失败 → 不阻止勾选，记 logger 后台重试

**验收标准**：
- 团队成员在 H5 看候选池列表
- 勾选当前选中数实时更新
- 选中超 50 时前端阻止
- 选中触发 AI 写草稿

**不做项**:
- ❌ 自动选中 top 30-50（团队人工把控品味，Q5 反对纯自动）
- ❌ 候选池实时计算（脚本周期性跑即可）

**用户流程**：

## 7. 跨主轴软目标 - Worker 上传后处理性能

### 7.1 子任务 5.7.1 - Worker 处理性能软目标

**用户目标**：骑手骑完上传 GPX 后，**大部分情况下（≥ 90%）5 分钟内看到处理结果**——不让"骑后即时反馈"瞬间因后端处理慢而流失。

**使用场景**：骑手骑完上传 GPX，等了 1-3 分钟看到 processing → 处理完弹反馈"你这次比上次快 25 秒"。极端情况（超大 GPX / worker 卡死）下沿用 v4 现有 10 分钟 timeout 兜底标 failed。

**功能范围**：
- 上传后处理时间**软目标**：≥ 90% 在 5 分钟内完成
- **5 分钟告警阈值**：超 5 分钟未完成 → 飞书机器人推团队群预警（**不阻断用户**，团队介入排查）
- **10 分钟硬上限**：沿用 v4 现有 timeout 机制（**不加严**）→ 超 10 分钟自动标 failed + 推通知
- worker 容器扩容（具体 replicas spec 决定）

**用户流程**：
1. 用户上传 GPX
2. 显示"处理中"
3. 大部分情况 1-3 分钟处理完 → 弹反馈
4. 极端情况超 10 分钟未完成 → 自动 failed + 推通知"上传处理失败，点击重试"

**页面/状态**：
- activity 列表 / 详情页：状态 processing / completed / failed
- 通知中心：失败通知（含重试入口）

**数据需求**：
- 沿用现有 activities 表 + status 字段
- v4 的 10 分钟 timeout 沿用（**不改 `_PROCESSING_TIMEOUT` 常量**）
- 新增"5 分钟告警检测"逻辑（spec 决定具体实施）
- 监控数据（处理时长）—— 飞书机器人推告警

**异常情况**：
- 处理超 5 分钟未完成 → 飞书告警（**不影响用户**，团队介入排查）
- 处理超 10 分钟 → 自动标 failed + 推通知 + 用户可重试（沿用 v4 现状）
- worker 卡死 → 10 分钟 timeout 自愈机制触发
- worker 重启时活动 stuck → 启动时扫 processing > 10 分钟的标 failed

**验收标准**：
- 用户上传 GPX 后 ≥ 90% 情况 1-5 分钟看到结果
- 极端情况超 10 分钟 → 自动 failed + 推通知（用户能重试）
- 团队监控告警群收到处理超 5 分钟的预警（无需阻断用户）

**不做项**：
- ❌ 实时进度条（v5 沿用现有 processing 状态，v6+）
- ❌ **5 分钟硬 timeout**（保持 v4 的 10 分钟 timeout，5 分钟仅做监控告警）

**来源**：Tim 问题 3b + 2026-04-28 修订为软目标
