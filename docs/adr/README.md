# velo 架构决策记录(ADR)目录

> 这里是 velo 所有重大架构和技术决策的 why 文档。**每份 ADR 回答一个"为什么这样选而不那样选"的问题**。
>
> ADR 是 velo 技术团队的集体记忆——一旦决策并 accepted,原文不改。如需修订,新开 ADR 标注 "supersedes ADR-N"。

---

## 1. 什么是 ADR,什么时候读它

**ADR(Architecture Decision Record)**是一份用来记录**关键决策背景和论证过程**的文档。它回答三个问题:

1. **当时面对什么选择**(决策情境)
2. **为什么选这个不选那个**(trade-off 论证)
3. **将来什么情况可能需要重新考虑**(触发重评估条件)

ADR **不是**:
- ❌ 当前系统的使用文档(那是 architecture-guide 和 dev-guide)
- ❌ 产品需求描述(那是 PRD)
- ❌ 运行规则(那是 CLAUDE.md 和 agent-rules)

**ADR 是**:
- ✅ 技术决策的历史档案,防止团队或 agent 将来"为什么当初选 X 不选 Y"的认知丢失
- ✅ 新成员快速理解"velo 为什么是现在这个样子"的入口
- ✅ 面对疑问("要不要改成 async?")时权威的先例参考

## 3. 按决策场景索引

### 我要写后端代码

先读 **ADR-001(同步强制)** + **ADR-002(任务队列 rq)** + **ADR-008(防火墙扩展)**。这三份是 velo 后端代码的底层约束,违反会导致代码层 reject。

### 我要加新功能或改数据库

必读 **ADR-008(防火墙扩展)**——新功能默认新表新模块,严禁修改核心表(users/activities/segments/segment_efforts)。

如果功能涉及地理:读 **ADR-005(坐标系分层)**。

如果功能涉及事件通知:读 **ADR-004(PR/KOM 活在 notifications)**。

如果跨业务模块共享工具(haversine / 时间窗口 / 字符串规范化等):读 **ADR-011(app/common 层)**——禁止把共享工具放任一业务模块。

如果功能涉及路线认知、concept、candidate、formal links、route_segments 或 collection memberships:读 **ADR-012(route cognition DB foundation)**——不要把 DB foundation 误当成 public API / admin UI / 自动 backfill。

### 我要做产品决策

先读 **ADR-006(小程序优先)** + **ADR-007(赛段贡献者众包)** + **ADR-010(不做实时导航)** + **ADR-013(骑前静态规划与骑中实时导航边界)** + `docs/agent-rules/product-decisions.md` **D-P07(Agent 是路线决策的核心交互层)**。

这些 ADR 与当前 D-P07 共同约束产品形态。ADR-013 仍为 Proposed / A1.1 in review，不得冒充 Accepted；ADR-009 已由 D-P07 取代，只保留作历史记录。

### 我要做部署和运维

读 **ADR-003(Caddy 反向代理)**。Caddy 是 velo 部署栈的基础组件。

### 有人提议"要不要改 X 决策"

- 先读对应 ADR,看当时的 trade-off 论证是什么
- 检查 ADR 里列的"触发重评估条件"——是否真的触发了?
- 如果真触发,新开 ADR(不改原文)、标注 "supersedes ADR-N"
- 如果没触发,用 ADR 反驳提议

## 4. agent 使用指南

agent **可以默认加载 ADR 的决策标题和核心结论**(本 README 的总表),但**不默认加载 ADR 全文**——全文 80-100 行每份,加起来 800+ 行,对 agent 日常工作 context 浪费。

agent 检索 ADR 全文的触发条件:

- 用户或 Tim 问"为什么 velo 做了 X 决定" → 读对应 ADR §理由部分
- 有人提议改变某个 ADR 决策 → 必读对应 ADR 的 trade-off 和触发重评估条件
- 架构或战略讨论需要权威先例 → ADR 是论证的根据

**与其他文档的关系**:
- `docs/agent-rules/product-decisions.md` 里的每条产品决策规则(D-P0N),都应引用对应 ADR
- `CLAUDE.md` 技术栈约束的背后论证在 ADR-001 / 002 / 003 里
- PRD 里提到"详见 ADR-N"时,去 ADR 读完整论证

## 5. ADR 写作规范

未来写新 ADR 遵循以下结构(参考现有 10 份):

1. **一句话核心决策**(开头必须有)
2. **决策情境**(当时面对什么选择,什么背景触发了讨论)
3. **考虑过的选项**(至少 2-3 个候选方案)
4. **决策和理由**(选哪个 + 为什么)
5. **trade-off**(放弃了什么,换取了什么)
6. **触发重评估的条件**(什么情况下这个决策可能需要反思)
7. **引用路径**(被哪些文档或代码依赖)

每份 ADR 80-120 行为佳。简洁、精确、可追溯。

**命名规范**:`{编号}-为什么{决策}.md`。编号不跳号,按决策时间顺序。

## 6. ADR 状态说明

- **Accepted**:当前生效的决策；已 Accepted 的历史原文不改
- **Proposed**:已形成候选裁决，等待 Orchestrator 审查；尚不能作为 Accepted 历史结论
- **Superseded**:被新 ADR 取代(原文保留,标注被哪份取代)
- **Deprecated**:不再适用但没有新决策替代(极少见)

一份 ADR 一旦 Accepted,**原文不改**。这是 ADR 制度的核心纪律——它是历史档案,不是动态文档。
