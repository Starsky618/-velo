# ADR-006: 为什么小程序优先,原生 App 后置到 v7+

## 状态
accepted (2026-04-22)

## 上下文

velo 需要决定产品的**客户端形态**:
- 微信小程序(velo 当前选择)
- iOS / Android 原生 app
- H5 Web 应用
- 或上述多端并行

行业参考: Strava / Komoot / iGPSport 都是原生 app 为主;Keep / 咕咚等中国运动 app 小程序 + app 并存;行者骑行主打 app。

选型决策点: v5 规划期(2026-04)Tim 提出"小程序功能上限低,未来肯定要转 app"——但**什么时候转 / 是否同步开发**是关键问题。

## 决策

**v1-v6 阶段**(2026-04 至 2027-Q2 预期): **只做微信小程序**,不开发 iOS / Android 原生 app。

**v7+ 阶段**(2027-Q2 之后): 根据监控的用户信号决定是否启动原生 app 开发,并优先用 React Native / Flutter 复用业务代码。

**长期**: 原生 app 启动后,小程序不废弃,作为"裂变入口 + 轻量使用场景",app 作为"深度用户主战场"**长期并存**。

## 理由

1. **用户在微信生态,小程序启动摩擦最低**。velo 目标用户("一线城市原子化骑手,渴望连接但不敢线下搭话")的社交通路是微信群。骑友拉人只要转发小程序链接,扫码秒进,比让他"下载个 app"转化率高 10 倍。原生 app 需要用户主动下载 + 注册 + 授权通讯录,每一步都流失。

2. **裂变链路必须微信闭环**。分享到朋友圈 / 微信群 / 私聊,链接必须是微信原生支持。H5 分享卡片差(ios wechat 内置浏览器限制多),原生 app 则完全绕开微信生态(app 只能分享 URL scheme + 截图,用户体验割裂)。

3. **工程成本不对等**。同样的业务功能,原生 app 需要 iOS 端(Swift + HealthKit + CoreLocation + StoreKit)+ Android 端(Kotlin + Google Fit + 高德 SDK + 各 OEM 推送适配),**每端约 3-4 人月 from scratch**,还要过 App Store + Google Play + 各手机厂商应用商店审核。小程序一次开发微信直接上架。

4. **"同步开发"是自杀动作**。v5 阶段 3 人团队已经捉襟见肘,分兵开 app 等于三个战场(后端 + 小程序 + app)都做不成。跨端方案(uni-app / Taro / Flutter)在涉及蓝牙 + GPS + 地图 + 后台定位时每一个都踩坑。

5. **小程序天花板虽然存在,但 v5-v6 够用**。小程序短板:后台持续 GPS 差 / 蓝牙连码表不稳 / 定位精度比 app 低 / Tab 数量限制 / 分包 2MB。v5-v6 核心价值(骑行数据展示 + 社交 + 赛段)**不依赖实时 GPS 录制**(用户用码表录,velo 导入 GPX),这些短板基本无感。

## 后果

### 正面
- 工程焦点集中,产品迭代速度快
- 裂变成本极低(微信原生分享)
- 不需要微信之外的运营体系(app 推广要 ASO / 信息流买量等)

### 负面
- 用户粘性天花板比 app 低(app 图标在手机主屏持续曝光,小程序要用户主动从"最近使用"找)
- 蓝牙码表 / 后台持续 GPS 等"深度骑行"场景目前不能做
- 严肃骑手对"小程序 = 不专业"有心智偏见(需要靠内容 / 社群建立专业感补偿)

### 触发转向原生 app 的信号

从 v6 开始主动监控以下指标,任一触发即启动 app 开发讨论:

- **用户明确表达要求**: 超过 50% 活跃用户在调研中说"希望有后台 GPS 记录"
- **功能被卡死**: 蓝牙码表连接成为高频付费意愿点,但小程序 API 限制做不到
- **规模压力**: DAU 突破 1 万,小程序加载/性能/分包限制开始频繁出现
- **商业化需要**: 精英社群 / 训练营等付费场景,用户希望有独立 app "显得专业"

## v7+ 启动 app 时的实现策略

不是"重做一个 app",是"把小程序的业务代码搬到更强的性能壳子":

1. **技术选型**: React Native 或 Flutter(优先,最大化复用小程序 JS/WXML 逻辑),不考虑原生 Swift/Kotlin 双端 from scratch
2. **优先平台**: 先 iOS(目标严肃骑手 iPhone 占比高),再 Android
3. **app 只做小程序做不到的**: 后台 GPS + 蓝牙码表 + 推送。其他全部与小程序共享后端 API
4. **运营分工**: 小程序作为裂变入口(用户在群里扫码进),app 作为深度使用(骑行中用)

## 违反代价

如果 v5/v6 期间 PR 启动原生 app 开发,会触发:

1. **三线作战失败**: 后端 + 小程序 + app 任何一条线都做不成,产品发布延期 6 个月以上
2. **资源稀释**: 3 人团队分兵,每条线代码质量下降,bug 堆积
3. **渠道分散**: 运营同时在小程序推广和 app store 推广,CAC 翻倍
4. **财务压力**: app 发布需要公司实体(个人开发者账号 iOS 99 美元/年 + Google 25 美元一次性,审核风险高)

**防御措施**: 
- PRD 每期明确写"本期不做 app",防止 scope creep
- 任何 app 相关需求写入 "v7+ 候选池",不占当前开发槽位
- CLAUDE.md 技术栈"不可变更"章节明确小程序优先
