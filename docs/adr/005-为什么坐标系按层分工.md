# ADR-005: 为什么坐标系按层分工(DB=WGS-84,小程序=GCJ-02,原始文件=源保留)

## 状态
accepted (2026-04-22)

## 上下文

地理位置数据涉及**三套坐标系**在不同场景生效:

- **WGS-84**: 国际标准坐标系,GPS 设备直接输出。PostGIS 和所有开源 GIS 软件默认使用。
- **GCJ-02**: 中国国家测绘局要求的"火星坐标系"。**高德地图 / 腾讯地图 / 微信内置地图**在中国大陆必须用此坐标。WGS-84 坐标显示在 GCJ-02 地图上会偏移 ~500 米。
- **BD-09**: 百度坐标系(在 GCJ-02 基础上再偏移)。velo 当前不涉及。

velo 需要在多处处理坐标:
- GPX / FIT 文件上传: 源数据一般是 WGS-84(码表 GPS)
- Strava API 返回: WGS-84
- PostGIS 数据库存储: 需要统一,因为空间查询(ST_DWithin)必须基于同一坐标系
- 小程序地图显示: 必须是 GCJ-02(否则骑行轨迹在地图上偏离实际道路 500 米)
- 赛段匹配运算: 坐标需要真实距离(WGS-84 作为真实地球坐标更准)

如果"一刀切"统一用 WGS-84 或 GCJ-02,都会出问题:
- 全部 WGS-84 → 小程序地图展示偏移
- 全部 GCJ-02 → PostGIS 空间运算误差(GCJ-02 加密算法非线性,ST_DWithin 的单位距离不精确)

## 决策

velo 采用**坐标系分层处理**策略:

| 层 | 坐标系 | 理由 |
|---|---|---|
| 原始文件存储 | **源保留**(通常 WGS-84) | 用户上传的 GPX/FIT 不做预处理,留档纯净 |
| PostgreSQL + PostGIS | **WGS-84**(SRID 4326) | PostGIS 原生,空间运算精确,科学计算用 |
| 内部服务间传递 | **WGS-84** | 后端所有业务逻辑、匹配算法、距离计算 |
| API 响应给小程序 | **GCJ-02** | 小程序地图组件渲染必需 |
| 小程序展示 | **GCJ-02** | 地图组件直接渲染 |

转换点在 **service 层 API 响应时**,调用 `parsing/coord_normalizer.py` 的向量化转换函数(numpy + xyconvert)。

## 理由

1. **PostGIS 空间运算必须用 WGS-84**。`ST_DWithin` / `ST_Distance` 在地理坐标上运算时,geography 类型以 WGS-84 为基础。如果把 GCJ-02 坐标存入 geography 字段,运算结果会有 0.5-1% 的距离误差(不致命但系统性偏差),且**赛段匹配的米级精度要求**(`match_tolerance` 默认 50 米)会被放大误差影响。

2. **小程序地图显示必须用 GCJ-02**。微信小程序 `<map>` 组件默认用 GCJ-02 渲染,坐标来源也假设是 GCJ-02。如果 velo API 返回 WGS-84,会出现"轨迹画在道路旁边的河里"的偏移。这是中国大陆用户必踩的坑。

3. **转换性能不成问题**。`xyconvert` + numpy 向量化 WGS-84 → GCJ-02 转换,10000 点耗时 < 10ms。API 响应 p95 < 300ms 不会被转换拖慢。

4. **分层而非一刀切,损失最小**。"一刀切"任意一边都会有代价:
   - 全 WGS-84: 小程序显示偏移,用户投诉
   - 全 GCJ-02: 空间运算误差 + 丢失原始精度 + 未来国际化困难(海外地图用 WGS-84)
   
   分层后,每一层只遵守本层的约束,各取所长。

5. **未来扩展空间**。如果未来海外用户出现,可以只改"API 响应给小程序"这一层 —— 境内转 GCJ-02,境外返回 WGS-84。中间层不用动。

## 后果

### 正面
- 空间查询精确,赛段匹配误差可控
- 小程序地图显示正确,用户体验无偏移
- 原始文件留档纯净,未来导出/互操作无损失

### 负面
- 坐标转换在 API 层是一个"必踩坑",新 API 加轨迹字段时容易忘记转换 → 测试要覆盖(看地图是否偏移)
- 代码复杂度比"一刀切"高,需要文档说明分层原则

### 触发重新评估的条件
- 如果国家测绘政策变化(概率极低,该政策从 2007 年稳定到现在)
- 如果 velo 主战场转向海外(GCJ-02 不再需要)

## 违反代价

如果未来某次 PR 把 GCJ-02 坐标存入数据库(或者相反,把 WGS-84 返回给小程序不转换),会触发:

1. **数据污染**: GCJ-02 存入 PostGIS 的 geography 字段,无法逆转,要 500 米级数据清洗
2. **赛段匹配失效**: `ST_DWithin` 单位变成"类度",50 米 tolerance 变成 5 公里或 500 米不等
3. **用户可见偏移**: WGS-84 返回小程序,轨迹在地图上偏 500 米 → 用户直接投诉"定位不准"
4. **数据一致性灾难**: 新老数据坐标系不一致,历史 segment 匹配全废

**防御措施**:
- 所有 API 响应轨迹字段必须过 `coord_normalizer.py`,单元测试覆盖"输入 WGS-84 输出 GCJ-02"
- Alembic 迁移中**禁止**手写坐标转换 SQL,必须 Python 代码做
- 架构 guide v2 §附录 B 明确标注坐标转换库
