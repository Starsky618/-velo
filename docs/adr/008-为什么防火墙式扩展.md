# ADR-008: 为什么防火墙式扩展(新功能默认新表/新模块)

## 状态
accepted (2026-04-22)

## 上下文

随着业务迭代,新功能持续增加。架构上有两种典型扩展策略:

- **胖表模式**: 给已有表(如 `users` / `activities`)加字段,逻辑加进已有 service。优势是代码集中,查询 join 少,短期性能好。
- **防火墙模式**: 新功能默认新表 + 新模块,通过外键或事件弱关联已有表。优势是核心稳定,功能失败时删模块不影响老数据。

v0-v4 期间 velo 混合使用两种策略,但 v4 末双审判 + 防黑盒化体检(2026-04-18)暴露了两起教训:

- `users.mute_notifications` bool 字段(v3 加)—— 免打扰功能,加到了核心 users 表
- `activities.activity_type` str 字段(v4 加)—— 运动类型种子,加到了核心 activities 表

这两个字段现在 "想砍代价大"。如果免打扰功能未来废弃,users 表要 Alembic 迁移删字段;如果活动类型决策改为分表(running 和 cycling 拆表),所有关联查询都要改。

## 决策

velo 从 v5 开始严格执行**防火墙式扩展**原则:

**新功能默认新表 + 新模块。严禁修改核心表**(`users` / `activities` / `segments` / `segment_efforts`),除非修 bug。

- ✅ **正例**: 积分系统建 `user_progress` 独立表,不在 `users` 加 `score` / `level`
- ✅ **正例**: 收藏赛段建 `segment_favorites(user_id, segment_id)` 多对多表,不在 `users` 加 `favorite_segment_ids` 字段
- ✅ **正例**: 活动标签建 `activity_tags(activity_id, tag_name)` 多对多表,不在 `activities` 加 `tags` jsonb 字段
- ❌ **反例**(v3 已发生): `users.mute_notifications` → 应该建 `user_preferences(user_id, key, value)` 配置表
- ❌ **反例**(v4 已发生): `activities.activity_type` → 应该建 `activity_types(activity_id, type)` 或按类型分表

## 理由

1. **核心表 = 业务根基,修改代价指数级增长**。`users` 有 10k 条,修字段需要 Alembic 迁移 + 全业务回归 + 跨模块 schema 同步。新建表只需要 "创建表 + 新模块引用",影响面可控。

2. **功能失败时风险隔离**。velo 是快速迭代的早期产品,新功能可能失败(用户不喜欢、技术方案不对、商业逻辑证伪)。新表 + 新模块的功能,**删模块不影响老数据**——反之在核心表加字段,即使功能废弃字段也留下,技术债累积。

3. **依赖方向清晰**。核心表稳定,新模块单向依赖核心表(通过外键 / 读查询),核心表不知道新模块存在。这是架构层面的"依赖倒置",符合 SOLID 原则。

4. **多人协作防冲突**。新模块 / 新表 = 独立文件 / 独立 migration,多人同时开发不会 git 冲突。改核心表 = 全员关注焦点,合并冲突多。

5. **回滚容易**。新模块 bug 上线,直接 docker-compose restart 对应 worker 或 revert 新模块 migration。改核心表 bug,回滚要恢复字段 + 老数据兼容,风险高。

## 后果

### 正面
- 核心表长期稳定,v0 定义的核心字段到 v100 都不动
- 功能试错成本低,删模块不伤数据
- 多人协作冲突少
- 代码可读性高,一个功能的代码都在一个模块里,不散落在核心模块各处

### 负面
- 模块数随功能线性增长,文件数更多
- 查询某些场景需要 join 更多表(但 PostGIS + 索引下性能不是问题)
- 相比胖表模式,起步时看起来"更复杂"(但长期复杂度低)

### 触发例外的条件

**允许修改核心表的唯一情形**:
- **修 bug**: 原字段设计有错,必须改(如字段长度不够、字段类型错误)
- **核心数据补全**: 字段本身属于核心概念(如用户的 openid 唯一标识),从一开始就该有但遗漏
- **性能优化**: 加索引、加冗余列(通常可以通过视图或物化视图替代)

**不允许修改核心表的典型场景**:
- 业务功能扩展(加积分、加等级、加标签、加开关)
- 非核心属性(如"偏好"、"设置"、"状态"等)
- 仅在某个场景使用的字段(如"活动 A 里某个赛段的排名快照"——应该存通知表而非 efforts 表,见 ADR-004)

## 违反代价

如果未来 PR 在核心表加字段(不属于上述例外):

1. **数据模式僵化**: 字段加了很难删,技术债累积
2. **跨模块耦合**: 其他模块如果读了这个字段,产生对核心表的反向依赖
3. **未来分表困难**: 如果增长到需要分表,冗余字段变成阻碍
4. **新成员学习曲线陡**: 核心表字段越来越多,要理解"这个字段是干什么用的"成本上升
5. **审查机制失效**: 一旦开了口子加了第一个,第二个第三个会接踵而来,防火墙就没了

**防御措施**:
- CLAUDE.md "防火墙式扩展" 原则明确记载(项目规则书第 18 行)
- 每次 spec 写完,双审判检查"是否修改了核心表",修改则必须说明为什么是例外
- 架构 guide v2 §7.2 明确列出反例和正例作为警示
