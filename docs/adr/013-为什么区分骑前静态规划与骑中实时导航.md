# ADR-013: 为什么必须区分骑前静态规划与骑中实时导航

> 核心决策：VELO 允许在出发前编译、验证和预览静态 Ride Plan，但继续禁止骑行中的实时导航与动态重规划。

## 状态

Proposed — A1.1，等待 Orchestrator 审查

## 决策情境

项目长期边界一直是不做实时导航，但旧产品规则把“路径规划”整体写成不做；这个统称混淆了两个用户阶段：

- 骑前，用户需要发现路线、组合接入段与返程段、比较距离和爬升，并选择静态方案；
- 骑中，设备需要持续定位、语音提示、偏航检测和动态重规划。

前者已经是 VELO 路线工具和骑手交流的基础，后者仍应交给专业地图或码表；如果不澄清，文档会一边禁止现有能力，一边要求 Agent 使用确定性路线服务。

## 当前代码事实

以下是本决策记录的现状，不代表本 ADR 授权新的运行时改动：

- `RouteBook` / `RouteVersion` 已保存路线及版本化几何底片；
- 腾讯 bicycling client 已能在骑前按起终点生成确定性路线，Route Draw 能请求贴路预览并暴露 Provider 失败；
- GLO-30 链路能计算路线海拔、爬升和可审计快照，导出链路能从可信版本生成受门禁保护的 GPX/TCX。

## 考虑过的选项

### 选项一：全部拒绝路线生成

- 好处：产品边界最简单，Provider 与验证成本最低；
- 代价：否定现有 RouteBook、腾讯路线、海拔和导出地基，无法形成完整的骑前路线体验；
- 结论：不采用。

### 选项二：VELO 自建骑中实时导航

- 好处：用户不必切换应用；
- 代价：需要全国路网、实时路况、后台定位、地图渲染和安全承诺，偏离团队能力与产品定位；
- 结论：不采用。

### 选项三：区分骑前静态规划与骑中实时导航

VELO 负责出发前的意图理解、静态方案生成、确定性验证和用户选择；外部地图或码表负责骑行中的实时导航。

- 好处：保留 VELO 擅长的路线发现和骑手决策，同时维持清晰的运行与安全边界；
- 代价：需要稳定的跨文档术语、明确的服务权力边界和外部设备衔接；
- 结论：采用。

## 正式决策

VELO 可以在骑行开始前：

- 理解骑手意图与约束，并在信息不足时追问；
- 使用已审核的核心路线、RouteBook 或 RouteVersion；
- 组合 `access + core + connector/branch + return`；
- 经受控高层服务调用地图 Provider，生成本次静态接入、连接或返程段；
- 由确定性服务计算几何、连通、距离、海拔并执行硬约束校验；
- 提供静态地图预览、候选比较和用户调整；
- 仅在用户确认且未来阶段与 Task Packet 明确允许时生成 GPX/TCX。

VELO 继续禁止：

- 骑行中的实时 GPS 跟随；
- turn-by-turn 或语音播报；
- 偏航检测与动态重规划；
- 实时路况导航或实时安全保证；
- 为导航持续后台采集位置；
- 离线导航地图和自建全国道路路由引擎；
- LLM 直接生成坐标、路线几何或 GPX。

## 权力边界

### Agent

- 可以理解意图、追问、比较候选、解释取舍；
- 可以引用确定性服务返回的路线结果；
- 不生成坐标或几何，不直接调用原始腾讯 client，不绕过 validator，不直接生成真实导出。

### Deterministic service

- 负责 Provider 调用、坐标和几何、连通、距离、海拔、硬约束校验与导出；
- 返回可追溯结果和失败，不把未知项包装成确定事实。

### User

- 在需要时确认精确起点；
- 选择最终 Ride Plan；
- 明确授权导出等有副作用的动作。

## 术语

- 使用“骑前静态规划”描述出发前的方案编译、验证、预览和选择；
- 使用“骑中实时导航”描述持续定位和实时引导；
- 使用“动态重规划”描述因偏航、路况或实时状态改变路线；
- 避免无时间边界地单独使用“路径规划”。

## 与 ADR-010 的关系

本 ADR clarifies ADR-010，does not supersede ADR-010；ADR-010 继续保持 Accepted、原文和哈希不变，本 ADR 只消除后来文档中的宽泛措辞。

## 后果与 trade-off

### 正面

- 现有静态路线能力与产品边界不再互相否定；
- Agent、确定性服务和用户的责任可以被后续合同机器化；
- 骑手获得完整骑前决策，同时骑中仍使用更可靠的专业设备。

### 负面

- 用户仍需把路线交给外部地图或码表完成骑中导航；
- 静态方案必须承担 Provider 失败、几何验证、版本失效和用户确认等额外门禁；
- 团队必须持续防止“静态预览”逐步漂移成后台定位或动态重规划。

## 非目标

- 本 ADR 不修改 runtime、合同、Provider 集成、导出、数据库、API 或小程序；
- 不选择 Agent SDK、Runtime 框架或长期 Memory；
- 不授权真实腾讯、DEM、生产数据库、真实导出、部署或生产流量；
- 不开始 A1.2–A1.5 或 A2–A5。

## 触发重新评估的条件

- VELO 的目标用户或产品定位正式转向必须自带骑中导航的人群；
- 外部地图和码表无法再承接骑中导航，且有真实用户证据证明替代方案不足；
- 法规、平台能力或安全责任发生实质变化，使当前分工不可行；
- 骑前静态方案的失败数据证明现有 Provider 与确定性校验无法满足核心场景。

重新评估必须另开 ADR；不得直接改写 ADR-010 或把本 Proposed 记录自行标记 Accepted。
