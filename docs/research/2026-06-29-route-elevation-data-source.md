# 路线导出海拔数据源调研

## 一句话结论

VELO 导出路线的最高优先级，是保留同一条路线的原始逐点海拔；中国合规高程数据只能作为第二优先级候选，未确认授权前不能写进生产导出链路。

## 用户故事

骑友小明在 VELO 下载一条路线，导入 iGPSPORT 后，App 不应该自己把路线丢给一套未知高程库重新算爬升。如果 VELO 手里有这条路线自己的精确海拔，就应该把 `<ele>` 或 `AltitudeMeters` 一起交出去，让目标 App 优先读我们的数据。

但如果 VELO 手里没有精确海拔，系统不能为了“看起来完整”去猜。猜出来的海拔一旦写进 GPX/TCX，用户看到的爬升数字会像坏尺子一样污染训练判断。

## 当前证据

| 证据 | 判断 |
| --- | --- |
| `content/routes` 本轮未检出 `<ele>` | 现有官方路线素材没有逐点海拔，旧路线不会自动变准。 |
| iGPSPORT 分享接口 `DetailsRoutesShare?routeId=106502` | 返回 `tracks[].alt`，说明部分公开分享路书确实带逐点海拔。 |
| iGPSPORT `routeId=106502` 实测 | 5017 个点，5017 个点都有 `alt`，海拔范围约 772.7m 到 1601.9m。 |
| 本轮几何比对 | `routeId=106502` 和当前官方路线素材不是同一条线，不能拿来回填 VELO 现有路线。 |
| 高德 WebService 官方目录 | 能看到路线规划等服务；本轮未在公开目录中确认可直接商用的逐点高程接口。 |
| 腾讯位置服务 WebService 官方目录 | 能看到路线规划服务；本轮未在公开目录中确认可直接商用的逐点高程接口。 |
| 百度地图开放平台首页 / 文档入口 | 能确认路线规划、轨迹等地图服务；本轮未确认公开逐点高程接口可直接用于 VELO 导出。 |
| 国家基础地理信息中心“国家基础地理信息数据库” | 官方页面明确包含数字高程模型数据库（DEM），但这更像成果/数据资源，不是开箱即用的线上 API。 |

## 数据优先级

### P0：同路线精确海拔

这层是默认应该先打通的正路：

- 用户上传 GPX/FIT 时，保留原始逐点海拔。
- 从用户已有骑行生成路线时，保留活动 trackpoints 里的海拔。
- 从 iGPSPORT 等外部公开路书补数据时，必须先证明是同一条路线；通过后只能把外部海拔贴到 VELO 坐标上，不能用外部坐标替换 VELO 路线。

已落地工具：

- `scripts/backfill_route_elevation.py`
- 默认 dry-run。
- `--apply` 才写库，且必须填写来源/授权说明。
- 几何不匹配直接拒绝。
- 写库时创建新的 `route_versions`，旧版本归档，不改旧版本底片。

### P1：中国合规高程补全

这层只能在授权确认后进入实现：

- 首选方向：自然资源部 / 国家基础地理信息中心 / 天地图体系下的 DEM 或高程服务。
- 必须确认：商业使用、批量查询、结果缓存、结果再分发到 GPX/TCX、成果标注和审图要求。
- 未确认前，不写代码接入。

### P2：目标 App 自行补算

这是最低优先级，只能作为兜底：

- VELO 导出二维 GPX/TCX。
- Garmin / iGPSPORT / 迈金 / Wahoo 自己补海拔。
- 用户可能看到和 VELO 页面不同的爬升，这是当前问题的根源。

## 不做的事

- 不把不同路线的 iGPSPORT 海拔拿来贴到 VELO 路线。
- 不用境外 DEM 做中国生产默认源。
- 不用“高德/腾讯/百度有地图 API”推导出“它们能合法提供逐点高程”。
- 不在没有授权或用户自有数据依据的情况下缓存或再分发第三方高程结果。

## 下一步

1. 用 `scripts/backfill_route_elevation.py` 对真实 route_book 先 dry-run，确认不同路线会拒绝。
2. 找到与 VELO 某条官方路线同源或同线的精确轨迹，再 `--apply` 生成新版。
3. 联系或继续核实自然资源部 / 国家基础地理信息中心 / 天地图体系的高程数据授权。
4. 授权明确后，再单独开 P1 高程补全 spec。
