# 路线导出海拔数据源调研

## 一句话结论

VELO 导出路线的最高优先级，是保留同一条路线的原始逐点海拔；中国合规高程数据只能作为第二优先级候选，未确认授权前不能写进生产导出链路。

## 用户故事

骑友小明在 VELO 下载一条路线，导入 iGPSPORT 后，App 不应该自己把路线丢给一套未知高程库重新算爬升。如果 VELO 手里有这条路线自己的精确海拔，就应该把 `<ele>` 或 `AltitudeMeters` 一起交出去，让目标 App 优先读我们的数据。

但如果 VELO 手里没有精确海拔，系统不能为了“看起来完整”去猜。猜出来的海拔一旦写进 GPX/TCX，用户看到的爬升数字会像坏尺子一样污染训练判断。

## 当前证据

| 证据 | 判断 |
| --- | --- |
| `content/routes` 本轮未检出 `<ele>` | 现有官方路线素材没有逐点海拔，旧路线不会自动变准。 |
| iGPSPORT 分享接口 `DetailsRoutesShare?routeId=106502` | 返回 `tracks[].alt`，说明部分公开分享路书确实带逐点海拔。 |
| iGPSPORT `routeId=106502` 实测 | 5017 个点，5017 个点都有 `alt`，海拔范围约 772.7m 到 1601.9m。 |
| 本轮几何比对 | `routeId=106502` 和当前官方路线素材不是同一条线，不能拿来回填 VELO 现有路线。 |
| 高德 WebService 官方目录 | 能看到路线规划等服务；本轮未在公开目录中确认可直接商用的逐点高程接口。 |
| 腾讯位置服务 WebService 官方目录 | 能看到路线规划服务；本轮未在公开目录中确认可直接商用的逐点高程接口。 |
| 百度地图开放平台首页 / 文档入口 | 能确认路线规划、轨迹等地图服务；本轮未确认公开逐点高程接口可直接用于 VELO 导出。 |
| 国家基础地理信息中心“国家基础地理信息数据库” | 官方页面明确包含数字高程模型数据库（DEM），但这更像成果/数据资源，不是开箱即用的线上 API。 |
| 全国地理信息资源目录服务系统 | 公开目录中能看到“数字高程模型（DEM）”成果条目，说明合规数据源方向存在；但它是目录/成果申请路径，不等于 VELO 可以直接缓存并再分发逐点高程。 |

## P1 调研结论（2026-06-29）

当前没有找到一个可以直接接入生产的“中国合规逐点高程 HTTP API”。

更准确的判断是：

- **国家基础地理信息中心 / 全国地理信息资源目录**：最像合规正路，能找到 DEM 数据资源和目录条目；下一步应该走授权、成果使用范围、缓存和再分发规则确认。
- **天地图体系**：官方站点有地图 API、网页 API、WEB 服务 API、数据 API 等入口；本轮未确认公开逐点高程服务合同。
- **高德 / 腾讯 / 百度**：公开能力主要是地图展示、搜索、路线规划、定位、轨迹等；本轮未确认它们提供可把结果写入 VELO GPX/TCX 并再分发的逐点高程接口。
- **Google Elevation / SRTM / 其他全球 DEM**：技术上能补海拔，但中国境内生产默认链路不采用，除非后续单独完成合规和授权判断。
- **仓库已有 SRTM/CGIAR 赛段 DEM**：`app/segment/dem_client.py` 已有 SRTM.py + CGIAR-CSI 90m 的赛段坡度估算链路，但这不是路线导出 P1 的合规精确源。它只能用于赛段内部估算/历史债务，不允许把结果写入用户下载的 GPX/TCX 当成 VELO 精确海拔。

P1 不能直接开写代码。正确下一步是拿到明确授权或购买/申请合规 DEM 成果，然后单独设计离线采样、缓存、来源标注和误差说明。

## P1 授权问题清单

联系数据方或申请成果前，必须拿到下面这些问题的明确答案：

1. **商业使用**：VELO 作为商业骑行平台，能否用于路线导出和用户下载。
2. **批量采样**：能否对一条路线按几十到几千个点批量取高程。
3. **缓存和落库**：能否把采样结果保存到 `route_versions.elevation_points_snapshot`。
4. **再分发**：能否把高程结果写进 GPX/TCX，让用户导入 Garmin / iGPSPORT / 迈金 / Wahoo。
5. **坐标和高程基准**：使用什么平面坐标系和高程基准，是否需要转换到 VELO 当前 WGS84 路线点。
6. **公开展示和审图**：在小程序页面展示海拔曲线、爬升数据，是否触发地图审核或成果标注要求。
7. **精度和适用范围**：格网分辨率、更新年份、山区道路误差、是否适合 5-10 米宽骑行道路。
8. **失败降级**：查不到点、海拔空洞、服务不可用时，是否允许保留二维导出。

这些答案没有拿到前，P1 只能停在“调研/授权”状态，不能进入生产代码。

## 数据优先级

### P0：同路线精确海拔

这层是默认应该先打通的正路：

- 用户上传 GPX/FIT 时，保留原始逐点海拔。
- 从用户已有骑行生成路线时，保留活动 trackpoints 里的海拔。
- 从 iGPSPORT 等外部公开路书补数据时，必须先证明是同一条路线；通过后只能把外部海拔贴到 VELO 坐标上，不能用外部坐标替换 VELO 路线。

已落地工具：

- `scripts/backfill_route_elevation.py`
- 默认 dry-run。
- 官方路线如果保留了仓库内原始 GPX/FIT，优先用 `--source-route-file content/routes/<slug>/track.gpx` 读取逐点海拔；文件必须在仓库目录内，防止误读服务器任意文件。
- 路书如果绑定了 VELO 源活动，优先用 `--use-route-source-activity` 读取活动 trackpoints；这是比第三方公开路书更干净的来源。
- 源活动回填时，逐点海拔给导出文件使用，总爬升沿用 `activities.elevation_gain`；dry-run 同时输出裸算 `computed_climb_m` 和最终写入 `climb_m`。
- `--apply` 才写库，且必须填写来源/授权说明。
- 几何不匹配直接拒绝。
- 写库时创建新的 `route_versions`，旧版本归档，不改旧版本底片。

### P1：中国合规高程补全

这层只能在授权确认后进入实现：

- 首选方向：自然资源部 / 国家基础地理信息中心 / 天地图体系下的 DEM 或高程服务。
- 必须确认：商业使用、批量查询、结果缓存、结果再分发到 GPX/TCX、成果标注和审图要求。
- 未确认前，不写代码接入。

### P2：目标 App 自行补算

这是最低优先级，只能作为兜底：

- VELO 导出二维 GPX/TCX。
- Garmin / iGPSPORT / 迈金 / Wahoo 自己补海拔。
- 用户可能看到和 VELO 页面不同的爬升，这是当前问题的根源。

## 不做的事

- 不把不同路线的 iGPSPORT 海拔拿来贴到 VELO 路线。
- 不用境外 DEM 做中国生产默认源。
- 不用“高德/腾讯/百度有地图 API”推导出“它们能合法提供逐点高程”。
- 不在没有授权或用户自有数据依据的情况下缓存或再分发第三方高程结果。

## 下一步

1. 继续把有原始逐点海拔的 VELO 路线优先回填；没有 `<ele>` 的官方 GPX 不允许伪补。
2. 联系或继续核实自然资源部 / 国家基础地理信息中心 / 全国地理信息资源目录 / 天地图体系的高程数据授权。
3. 授权明确后，再单独开 P1 高程补全 spec，明确采样精度、缓存周期、来源标注、再分发边界和失败降级。
4. 在 P1 之前，公开路线缺海拔时继续返回二维文件，不把目标 App 的 DEM 结果写回 VELO。
