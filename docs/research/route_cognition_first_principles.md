## 2. 独立第三方总评

### 会话 A 的评价

方向发现是正确的，结束判断过度乐观。

它找到了 VELO 路线产品真正有区分度的交互原子：不是给骑手更多路线文案，也不是先造路线网络，
而是让地图、坡型、照片和有界事实沿同一公里位置互相解释。它还正确区分了人类能识别的入口与机器
精确的几何起点。

但它随后把正确的类型系统 `Plan / Route / Activity` 延伸成未经验证的生态飞轮，并把授权、版本、
贡献、认证等后台约束搬进第一版前台。会话末尾所谓“逻辑已经闭环”，最多只能说对象语义初步闭环，
不能说产品体验闭环。

### 会话 B 的评价

不是“什么都没做成”，而是把多个局部成功错误地放进了同一个战略记分牌。

- Plan 的真实用户链路确实闭环，这是可复查的产品成果。
- 海拔实验反复推翻漂亮候选，留下了比“找到一个算法”更重要的失败边界。
- 公共 Route 最关键的同里程认知体验仍未实现，也没有陌生骑手证据。

会话失控的根因不是单纯上下文太长，而是三个终点不断换位：

1. 公共 Route：怎样准确看懂路线；
2. 个人 Plan：怎样规划、保存和带走；
3. 海拔 R&D：怎样证明预计爬升接近外部真值。

每条线都值得做，但一条线的局部通过不能替另一条线宣布完成。错误的恢复合同又把当时的局部
“下一步”固化成全局方向，因而比没有恢复点更容易稳定跑偏。

### 合并裁决

> 保留三个名词，冻结生态箭头，从 V0 删除骑手认证与信誉制度；把产品资源重新压回“一条真实路线怎样被陌生骑手准确看懂”。

`Plan / Route / Activity` 只保留为语义边界：

| 对象 | 用户问题 | 当前证据 | 当前动作 |
|---|---|---|---|

Activity 匹配、贡献授权、路线纠错和版本治理可以作为未来约束研究，但不能再模拟成 V0 的用户主流程。

## 3. 路线认知的第一性原理

### 3.1 路线认知的本质是压缩四类误判

陌生路线的根本问题不是“缺少更多字段”，而是骑手必须用很短时间预测一段自己没有骑过的空间。
VELO 的价值是减少四类可观察的误判：

| 误判 | 骑手会错在哪里 | 最直接的表达 |
|---|---|---|
| 定向误判 | 找错入口、搞反方向、误解起终点 | 有方向的地图、入口地标、清晰边界 |
| 体力分布误判 | 只看平均值，不知道什么时候最难 | 全程坡型、持续区间、共享公里位置 |
| 现实识别误判 | 到了关键路段也认不出来，无法把图表对应到道路 | 同位置照片或人工核实的现实线索 |
| 认知边界误判 | 把预计当实测、把未知当安全、把单段当完整骑行 | 来源、时间、覆盖区间；无法可靠表达的信息隐藏或撤下 |

一个页面元素只有在减少其中至少一类误判时才有存在理由。这也解释了为什么共享里程轴比继续添加
独立卡片更重要：它把空间、体力和现实线索变成同一个模型，而不是三份需要用户自己拼接的信息。

### 3.2 产品终点是用户脑中的模型，不是页面上的信息量

一条路线被“讲清楚”的判据，不是卡片齐全、数据库字段齐全或文案写得长，而是骑手离开页面后仍能
准确复述：

1. 从哪里进入、朝什么方向骑；
2. 全程体力压力怎样分布；
3. 哪个路段最会改变自己的判断，它在地图哪里、现实中看起来怎样；
4. VELO 描述的路线到哪里结束，页面事实的证据边界是什么。

总距离、总爬升和平均坡度只是摘要，不能单独形成这套模型。

### 3.3 V0 的主体是一条有方向、边界稳定的路线

- 先做 `奥申正爬` 这类固定起终点的公共道路爬坡；不先解决组合、返程、环线和全国路线库。
- 方向会改变入口、终点、坡型和体验，不能靠机械反转生成另一条公共 Route。
- 一条路线自身必须在没有用户贡献、没有社交证明、没有 Activity 的情况下产生完整的 N=1 价值。

### 3.4 共享里程轴是核心交互，不是锦上添花

地图回答“在哪里”，坡型回答“体力怎样变化”，照片回答“现实中看见什么”，POI/路况/风险回答
“到这里要注意什么”。如果四者没有共同的里程坐标，用户仍需自己完成拼图。

V0 至少需要一种真实的联动：用户在完整坡型或地图上指向某个公里位置时，另一个视图同步定位，
并展示该位置唯一最有判断价值的现实线索。静态地图旁边放一张静态坡型图，不算这个核心命题已经实现。

### 3.5 先总览，局部细节只在用户动作后出现

- 默认稳定展示全路线、完整坡型、方向和少量关键指标。
- 不自动缩放到局部，不用瞬时最大坡度制造噪声或恐吓。
- 持续坡段比单点峰值更符合骑手体验，但 500m、1km、100m 着色等具体窗口仍只是算法候选，
  不能因会话里口头同意就变成事实。

### 3.6 人类入口与机器起点可以精度不同

- 骑手需要地标、地图位置和必要时的照片来认出入口。
- 几何、导出和同里程绑定需要精确起点。
- 两者应有关联，但不强迫上传者用箭头、朝向和额外说明承担机器精度成本。

### 3.7 只展示有界事实，不制造整条路线认证

- 一张照片只有在 GPS、拍摄时间等元数据存在并完成路线位置绑定时，才证明该位置/时间的现场画面；
  它不自动证明方向或 RouteVersion。
- 一次 Activity 只证明当次设备记录，不自动修改公共 Route。
- 某个固定赛段或算法只证明它覆盖的区间与指标，不能给整条路线、安全性或“经典程度”盖章。
- 可选照片缺失时模块可以消失，不要求显示“暂无实景”或“不确定”占位；风险、海拔或路况没有
  可靠依据时不得编造，也不得让页面结构暗示已经确认安全。前台究竟隐藏、撤下还是说明来源/覆盖，
  仍需按信息类型验证。

### 3.8 稳定路线事实与当天决策分开

Route V0 先讲稳定本体：几何、方向、入口、完整坡型和可核事实。“今天是否适合骑”、施工、天气、
临时封闭等动态信息属于准备骑行或外部服务，不进入第一刀。

## 4. 两场会话的四态决策账本

### Tim 已拍板的当前 V0 约束（不等于行为验证）

这里的“拍板”表示产品范围和表达约束已经明确，不表示陌生骑手已经用真实行为证明 UX 有效。
目前只有 Plan 的规划→保存→导出→iGPSPORT 属于真实路径验证。

- 单条路线先于组合与路线网络。
- V0 先让陌生骑手准确看懂路线，不负责回答今天是否去骑。
- 有方向的 Route 是认知主体；不自动反向。
- 地图、完整坡型、照片/POI 共享里程轴是最值得验证的核心。
- 可视化优先；照片等增强层不是路线存在的门槛。
- 照片交互默认采用地图聚合点 + 单一查看器 + 按路线里程滑动，不把照片铺成相册；这是 Tim
  已拍板的设计默认，真实用户效果仍未验证。
- 多路线发现暂以 `城市 → 骑行地 → 路线` 为设计默认；它不进入本轮单路线实验，也尚未经过
  真实用户验证。
- 人类入口表达与机器精确起点分层。
- 不做综合难度分、瞬时最大坡度和整条路线认证。
- Route 看懂后只保留一个“准备骑行”行动尾钩；它不能反过来吞掉 Route。
- 页面、导出和同一版本应消费同源成品；一致性是必要条件，不是准确性证明。

### 已否决的具体机制（无新证据不得换名字重开）

- 当前路线组合、连接网络、虚构区域多边形、虚构路线数量和游戏化 3D 地形卡。
- 强制照片朝向、箭头和冗长上传说明。
- 直线补给距离、自动反向、综合难度分和“官方真路线”二元标签。
- “三把钥匙”认证、“至少一位实骑者确认”、骑手信誉、投票和认证徽章。
- Plan 自动晋升为 Route、Activity 自动公开或自动修改 Route。
- 把导出成功、代码通过或数据库完整当作路线认知完成。
- 把生态治理模拟算进 Route V0 完成标准。

### 真未决，需要真实实验

- 陌生骑手是否能在两分钟内复述入口、方向、整体坡型和决定性路段。
- 同里程交互是否比静态并排信息显著降低理解成本。
- 已拍板的统一照片查看器是否真的比页面内嵌照片更能帮助陌生骑手定位现实路段。
- `城市 → 骑行地 → 路线` 已是 Tim 当前拍板的多路线发现默认，但不是路线认知第一性原理；
  它在真实多路线用户行为中是否成立仍未验证，也不进入本轮单路线切片。
- Route 的“准备骑行”怎样自然交给已有 Plan 或外部工具。
- 公共 Route 如何出生；当前可先人工策展少数真实路线，不先造通用治理制度。
- 补给、风险、施工和当天状态采用何种可持续数据源，以及各类信息应隐藏、撤下还是说明证据范围。

### 后来明确推翻

- “Activity 匹配→授权→贡献→版本治理应该进入第一版主流程”。
- “全国道路海拔真值是手绘 Plan 或 Route UX 的首发前置条件”。
- “候选能运行、开发集好看，就可以先接生产再继续验证”。
- “有一个唯一恢复合同就不会发散”。恢复点若违背用户后来的裁决，会更稳定地带歪下一场会话。

## 5. 海拔实验：必须保存的结论

### 产品级结论

1. 当前 GLO 成品链是可运行、可重放的基线，不是已通过准确性验收的能力。
2. `Activity` 保留码表原始主值；`Plan / Route` 显示 VELO 预计值。单条 Activity 不得直接、
   自动覆盖既有公共 RouteVersion；未来可把多条通过质检的 FIT 作为离线聚合校准证据，审核后生成新版本。
3. 同一版本、同一几何、页面与导出同源能消除表示漂移，但不能证明绝对准确。
4. GLO 继续作为统一底座；ALOS 与 FIT 只作离线证据。Tim 自述已获 Strava 官方团队书面批准，
   可将公开赛段用于海拔研究、拟合和校准参考；本轮未核验授权原文，不外推到原始数据再分发或公开镜像。
5. 当前产品重心回到 Route 认知。海拔 R&D 暂停；不引入高德、RTK、新地图源或新实体。

| V0 × M0 | 隧道局部改善，但整线仍高 `449.1m`；bridge 与 M0 破坏保护样本 | 局部机制成立仍可能整体失败 | 误差抵消可冒充成功 |
| 腾讯保存 RouteVersion | r0/r1/r2 长度差 `+6.72%/+6.62%/+10.27%`，均几何不匹配，未运行海拔 | 保存链闭环；腾讯替代路线不能绑定目标线 | 换高德继续同类递归是当前产品下一步 |

正式 P3 资格仍是固定坡 `0/30`、全新长路线 `0/18`。这表示还没有正式盲测发布资格，
不表示所有开发实验都没有数值或没有知识价值。

## 6. 两场会话暴露的流程教训

### 6.1 把四条工作线永久分开验收

1. Route 认知 UX；
2. Plan 规划与导出；
3. Activity / 贡献生态；
4. 海拔算法 R&D。

任何一条的通过都不能替另一条宣布完成。

### 6.2 禁止跨级升格

- 数据齐全 ≠ 路线可信；
- 页面/导出一致 ≠ 外部准确；
- 模拟交互跑通 ≠ 用户需要；
- 开发集通过 ≠ 盲测通过；
- 测试绿 ≠ 真机用户闭环；
- 局部机制成立 ≠ 整个产品成立；
- agent 一致赞成 ≠ 用户验证。

### 6.3 候选只能单向晋升

```text
IDEA → DEV_PASS → BLIND_PASS → SHADOW → PROD
```

任何硬门失败的候选不得因为“暂时没有更好的”进入生产。参数、实现、样本或标签一旦揭示后又修改，
该批样本立即降为开发证据。

### 6.4 每次恢复先读四态账本，再决定是否有新问题

开始任何新研究前，先在本文中查 `已确认 / 已否决 / 真未决 / 后来推翻`。如果问题已有裁决，
新一轮必须拿出能改变裁决的新证据，不能只换术语或换 agent 重新问一次。

恢复点必须同时写：

```text
CURRENT_GOAL
VERIFIED
FAILED
DO_NOT_REOPEN
NEXT_EXPERIMENT
STOP_CONDITION
```

用户最后一次明确裁决永远覆盖旧 `NEXT_ACTION`。

### 6.5 新实体或数据源必须减少当前命名的不确定性

新增数据库实体、地图源、算法层或外部服务前，只问：

> 它减少了 Route 认知 V0 的哪一个已命名错误判断？

答不上来就不做。当前高德、RTK、全国真值底座、Observation 新实体和贡献治理都答不上来。

## 7. 建议的下一刀：最小可检验路线认知实验

本节是独立第三方建议草案，不是已经由 Tim 确认的招募计划或验收合同；受试者来源、人数和门槛
应在真正执行前单独确认。

### 唯一研究问题

> 同一里程轴上的地图、完整坡型和一个现实线索层，能否让陌生骑手准确理解奥申正爬？

### 最小切片

- 默认入口就是一条 `奥申正爬`，不经过城市、区域和组合页面。
- 页面稳定显示方向、入口/终点、准确轨迹、完整坡型和少量人工核过的预计指标。
- 用户触摸坡型或地图时，另一视图同步到相同公里位置。
- 只加一个现实线索层：优先使用已有真实照片；没有合格照片时用一个人工核实的入口或决定性路段 POI，
  不造占位图、不造安全事实。
- 一个“准备骑行”CTA 作为尾钩；本轮只验证交接是否易懂，不扩 Activity、授权、版本治理或设备管理。
- 不新建 schema、不换数据源、不修改海拔生产算法。

### 验收

建议找 3 位不熟悉奥申的严肃公路车骑手做观察测试。两分钟浏览后关闭页面：

1. `3/3` 能说对入口、方向、整体坡型和路线终点；
2. 至少 `2/3` 能在地图上指出决定性路段，并说明它怎样改变了自己对整条路线的理解；
3. `0/3` 把这条正爬误解为完整环线、自动返程或认证安全路线；
4. 所有被测试者看到的安全、路况和海拔事实均能追溯到有界证据；缺证据的模块隐藏或撤下，
   且没有人因此误以为页面已经确认安全。

如果失败，先改信息关系与交互，不用新增数据库、算法或路线数量掩盖失败。

## 8. 当前第一性原理问题

下一轮讨论不应再从“页面放哪些组件”开始，而应从这个可反驳的问题开始：

> 骑手离开页面 30 秒后，最少必须能复述哪四件事，才算 VELO 真正把这条路线讲清楚？

当前推荐答案是：`入口与方向 / 整体坡型 / 决定性路段的位置与现实样貌 / 路线与证据边界`。
下一版原型中的每个元素都必须能解释自己帮助了其中哪一项；否则删除。
