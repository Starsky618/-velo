## 0. 战略定位

### 0.1 为什么开训练分析这条线

velo 当前定位混合了"骑行社交"+"训练记录"。现在做战略分流，开**两条独立并行的产品赛道**：

- **训练分析线**（本路线图）：服务"认真练车的中国业余骑手"
- **骑行社交线**（另立路线图）：服务"日常通勤 + 周末骑"的大众用户

> ⚠️ **Tim 待拍**：两条线各自的目标用户规模 / 渗透率假设我没真调研 / 留空。Tim 后续填具体数字。

两条线**几乎不碰对方的代码** — 训练分析全是"加字段 + 算法 + 新页面" / 社交是"explore / 通知 / 排行榜增强"。可由 Tim 和 CCF 分别主导。

### 0.2 训练分析线的核心用户故事

> **认真练车的张三**：他有功率计 + 心率带。每天骑完车 / 想看到的不是"我骑了多远多累" / 而是"我今天到底是变强了还是过累了 / 该不该继续按计划训练"。
>
> 现在他用 intervals.icu / Strava Premium / TrainingPeaks / WKO5 — 这些工具年费 60-300 美元 / 都是英文 / 中国骑手付费意愿低但需求真实。
>
我们打造一个**中文 + 集成 Strava + 跟当地骑友比对**的训练分析平台。

**Tim 2026-05-20 拍**：**上线初期完全免费 / 未来可能收费**。具体定价 / 收费时机 / 免费 vs 付费功能边界等用户量起来后单独决定 / 本路线图不展开。

### 0.3 上线策略

**Big Bang 完整版**（4-5 个 sprint / 6-8 周）。

理由：100 用户量级不靠"持续小步快走"维持粘性 / 而是靠"上线时给业内人留下'velo 是认真做训练分析的'印象"打开口碑。

发布动作：完整版 ship 后写 1 篇深度长文（"velo 训练分析背后的科学 / 怎么用 CP 3-param + 心率融合估 FTP"）→ 投到知乎 / 小红书骑行圈 / 推单车圈 KOL。

## 1. 5 个模块全景

### 模块 A：单次活动评分 + FTP 智能化（Sprint 9）✅ 2026-05-21 ship

> **小明骑完今天的间歇训练**：打开 velo 详情页 → 看到 "今天 TSS 95 / IF 0.85 / NP 215W ← 接近你 FTP 的强度" → 心想"这次练得到位 / 跟训练计划吻合 / 明天该恢复骑"。
>
> **如果小明刚注册没填 ftp**：进设置页 → 系统说"我扫了你最近 5 条活动 / 估算你 FTP 约 220W / 用这个？"→ 小明确认 / 立刻所有历史活动开始显示功率区间分布 + TSS。

**给用户什么**：
- 详情页加 NP / IF / TSS 三个数字（每次骑完都有"今天到底有多累"的量化分数）
- 系统首次帮新用户估 FTP（不用自己查"什么是 FTP"+ 测试）
- 体重输入 + W/kg 显示（用户能看自己档位）
- 用户骑出超过预估 → 系统提示"你今天突破了 FTP / 更新？"

**核心问题解决**：用户进 velo 第一周就有"被服务"的感觉 / 不用自己研究术语。

**工作量**：~10 天（最复杂的一期 / 含 snapshot_ftp 地基架构）。

**详细 PRD**：`docs/prd/sprint-9-prd.md` ✅ ship 完工 / 8 task + 9 hotfix（详 `docs/changelog.md` 2026-05-20→21 段）。

**P1 tech debt**：ftp_estimator 算 Tim ftp=117W vs 真实 1200s best 250W 差 100W+（`docs/tech-debt.md` P1）/ Sprint 10 后开"FTP 估算精度专题"。

---

### 模块 B：训练负荷曲线 PMC（Sprint 10）

> **认真练车的张三**：3 周后周末打开 velo → 训练日历页 → 看 30 天曲线图 → 三条线：
>   - 绿线（健身度）从 50 涨到 68 → "我变强了"
>   - 黄线（疲劳度）今天 80 → "上周末连续大强度后没歇好"
>   - 蓝线（状态）今天 -12 → "还能再扛一两天 / 周中安排个轻松骑"
>
> 他不用打开 intervals.icu 网页 / velo 直接给。

**给用户什么**：
- 每天自动算 CTL（健身度）/ ATL（疲劳度）/ TSB（状态）三个指标
- 训练日历页：30 天 / 90 天 / 全年曲线图
- 状态评分四档（状态好 / 一般 / 累 / 过累）/ 文字提醒

**核心问题解决**：用户能看到"过去 6 周训练有没有真见效"+ "现在适不适合继续上量"。

**工作量**：~7 天。

**依赖**：模块 A 的 TSS 已经在每条活动写入 DB。

---

### 模块 C：训练分布分析（Sprint 11）

> **认真练车的张三**：训练页有个饼图 → 看自己最近 6 周时间分布：
>   - Z2（耐力区）60%
>   - Z3-Z4（节奏 / 阈值）35%
>   - Z5+（高强度）5%
>
> velo 提示："你属于 Sweet Spot 训练分布 / 适合时间紧的车手。如果你想再上一个台阶 / 建议改成 Polarized 80/20 / 拉长 Z2 时间到 80% / 增加 Z5+ 高强度间歇到 15%"。

**给用户什么**：
- 最近 6 周训练时间分布饼图（按 power_zones 累计时间）
- 自动分类（Polarized / Pyramidal / Sweet Spot / Threshold）
- 训练分布建议（教练级文字 / 跟用户当前类型对比）

**核心问题解决**：用户知道自己训练有没有结构 / 还是瞎骑。

**工作量**：~5 天。

**依赖**：模块 A 已 ship（power_zones 已经按 snapshot_ftp 算好）。

---

### 模块 D：每日推荐 / LLM 教练总结（Sprint 12）

> **认真练车的张三**：早上 6 点打开 velo → 动态 tab 顶部大卡 → 点开"今天"页 → 看到 4 段卡片：
>   - 标题"低风险 Zone 2 有氧打底日"
>   - 综合分析（融合训练负荷 + 天气 + 训练目标 + 最近活动）
>   - 训练决策（zone / 时长 / 强度）
>   - 恢复预警 / 风险提醒（如有）
>
> 类似 Strava Athlete Intelligence / 但中文 + 接和风天气 + 跟 velo 训练负荷集成。

**给用户什么**：
- 用户在 profile 填一次训练目标（5 选 1：提升有氧 / 提高 FTP / 备战长距离 / 减脂 / fun）
- 早上 6 点 cron 跑 / DeepSeek 写 4 段卡片 / 实时融合训练负荷 + 当地天气 + 历史活动
- 动态 tab 顶部大卡 + 完整"今天"页 / 三层用户分层（no_data / partial_data / full_data）
- 用户能手动刷新（每天 4 次）

**核心问题解决**：用户不用自己看曲线分析 / 系统按真数据写出"今天该怎么骑" / 装饰层不够好用 → 升级到主动指导层。

**工作量**：~10 天（LLM 版 / 含和风天气接入 + coach_outputs 表 + DeepSeek prompt + 前端"今天"页）。

**依赖**：模块 A + B + C 全 ship（必须有 TSS + CTL/ATL/TSB + 功率区间）。

**详细设计**：`docs/superpowers/specs/2026-05-20-coach-engine-design.md` v0.1（含产品形态 + 数据架构 + 算法 + LLM 流水线 + 前端 + 验收 / 已 brainstorm 走完 Step 1-5）。

---

### 模块 E：恢复 / 健康监测（**永久不做** / 2026-05-20 reality check 推回）

> 原 v0.1 设想：接入小米手环 / 苹果健康 / 华为运动健康 → 拿 HRV + 静息心率 → 教练建议升级。
>
> **2026-05-20 research subagent 实证 velo 永远拿不到 HRV / 静息心率**：
> - 微信小程序 `wx.getWeRunData` **只返步数** / 没心率没 HRV
> - 微信小程序**不能直接调 Apple HealthKit**（开发者社区硬限制）
> - Strava API 官方明文**不返 HRV / 静息心率 / 恢复评分**
> - 蓝牙手环可连但每品牌协议不一 / 体验差
> - HRV 真测 = Polar H10 胸带 / Garmin 手表（velo 用户 < 3% 有）
>
> **结论**：Whoop / Garmin 模式的壁垒是硬件不是软件。velo 100 用户量级 + 微信小程序入口 → 永久不做"假装有 HRV"的功能。装作有一被识穿就是信任级事故。
>
> 详细实证：`docs/superpowers/specs/2026-05-20-coach-engine-design.md` §6.2

## 6. 风险

### 6.1 算法风险

- **CP 3-param 拟合失败**：用户日常骑行没"全力段" → 拟合曲线退化。**兜底**：返 NULL / 让用户手填 ftp。
- **心率漂移加权干扰大**：用户没心率带 → 退化为不加权的 CP 3-param。
- **TSS 公式依赖 NP + FTP**：NP 已有 / FTP 由 snapshot_ftp 给 / 不引入新依赖。

### 6.2 产品风险

- **新用户被弹窗淹没**：模块 A 一次有 3 个弹窗（首次填 ftp / 体重输入 / Breakthrough）。Sprint 9 PRD 需严格定义弹窗触发顺序 + 频次 + 静默期。
- **训练分析过度复杂吓走轻度用户**：训练分析页面在"我的"页二级入口 / 不挤首页 / 不强推。轻度用户感知不到 / 重度用户主动找。

### 6.3 工程风险

- **Sprint 9 工作量集中**：8 task / 10 天 / 风险点多。**兜底**：Sprint 9 PRD 写完先三审 → 拆 task 卡时严格按"反向条件"派 subagent → 真用回归不一次性测 8 个 task。
- **Sprint 10-12 依赖 Sprint 9 ship 质量**：Sprint 9 如果 snapshot_ftp 架构没设计好 / 后续全部坍塌。**兜底**：Sprint 9 ship 后留 1 周观察期再开 Sprint 10。

## 7. 不做项（明确推到未来）

- **训练计划编辑器**（用户自己排周训练）→ B 端工具 / 我们 100 用户量级不做
- **跟教练协作**（教练后台 / 评论运动员训练）→ B 端 / 不做
- **比赛日预测**（"如果你按计划训练到 8 月 1 日 / 你的状态会是 X"）→ 复杂建模 / 留到完整版后
- **AI 教练对话**（用户主动跟 LLM 聊训练）→ v2+ 再考虑（区别于模块 D：D 是定时推 4 段卡片 / 对话是用户主动跟 LLM 互动）
- **设备数据接入**（功率计校准 / 室内骑行台 ANT+）→ 硬件赛道 / 不做
- **Persona Engine（老登嘴贱 NPC 便利贴）已砍**（2026-05-20）→ 一个 sprint 战略失误的复盘 / 装饰展示层不该上 sprint 主线 / 详见 memory `feedback_decoration_vs_guidance_velo_persona_lesson.md` + 全局 CLAUDE.md §2.1 "装饰展示 vs 主动指导"原则
