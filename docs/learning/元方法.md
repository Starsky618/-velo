# 元方法

> 4 天 Persona Engine sprint 学到的 4 条规律。
>
> **使用流程**：新窗口接 NPC bug 修完后 / 我回头读这 4 篇做整 Sprint 复盘 / 把这份 .md 和 `VELO学习笔记.docx` 里的手写笔记融合（docx 偏**个人感悟** / md 偏**方法论结构化**）。

---

### 1. CEO 反问能戳穿"简化偷懒"

**真事**：我推"历史活动用现在段位算 NPC"——简化版本 / 想偷懒。你一句"那是按啥标准？所有历史都按今天？" 戳穿。我立刻意识到 SQL window function 一句话能算"当时段位" / 一点不复杂。

**道理**：下属/AI 给"简化方案"时 / **反问一个边界 case**就能验证是真简化还是逃避复杂度。问句模板：

- "那 X 维度的真实情况怎么处理？"
- "如果用户在 Y 边界呢？"

5 秒成本 / 防 30% 的偷懒方案。

**可迁移**：所有团队管理 / 不止 AI 协作。下属做产品方案 / 工程方案 / 设计方案 / 你都问一个边界 case / 是简化派 vs 偷懒派的照妖镜。

---

### 2. "看不到 X" 第一动作不是猜应用层 / 是看时间戳

**真事**：你报"看不到 NPC" / 我没去猜 endpoint bug / 没去猜 schema 错 / 5 秒做了 3 件事——`docker compose ps`（看 worker 容器多久前 rebuild）+ `psql persona_outputs`（看表里有没有数据）+ `docker logs worker`（看新代码有没有跑）→ 锁定"worker 容器没 rebuild"。

**道理**：用户报"X 不工作" / 99% 的猜测都是猜"应用层 bug" / 但真根因经常是**容器/进程状态错位**。第一动作永远是看**时间戳**（这个 service 是不是最近 rebuild？日志最后一次新代码 log 是什么时候？）/ 不是看代码逻辑。

**可迁移**：去年 admin H5 502 事故是同一个模式（猜了 30 分钟应用层 / 真相是 nginx 缓存了旧 IP）/ 这次 NPC 不显示是同一个模式扩展（猜应用层 / 真相是漏 rebuild worker）。**两次同模式 = 这是个真规律 / 不是偶然**。值得"沉淀到肌肉记忆"。

---

### 3. "我自己懂了" ≠ "外人懂了" — 同步是独立工作

**真事**：4 天 Sprint 全 ship / agent memory 满满当当 / 但 `docs/architecture-guide.md` + `docs/data-flow-guide.md` + `docs/tech-debt.md` **零处** Persona Engine 引用。一直到跑 neat-freak skill 才发现。

**道理**：写代码自己感觉良好 ≠ 文档对**外部读者**说明清楚。新人加入 / 其他 agent 接手 / 半年后的你回来看 / 都需要**独立同步动作**。这件事不会"顺便发生" / 必须刻意做。

**可迁移**：所有交接 / 上线 / 项目收尾——"我自己懂"和"文档讲清楚"是两件事 / 不能合并执行。每次大变更后 / 必须**独立留 30 分钟**专门做对外文档同步（neat-freak skill 就干这个）。

---

### 4. "cycle 化"远胜"batch 化"（批量内容生产的关键）

**真事**：168 条 NPC 文案不是一次性丢给你 200 条让你审 / 而是 8 轮 cycle / 每轮 8-10 候选 / 每轮 < 5 分钟你的时间 / 累计不到 1 小时。每场景独立闭环 / 你的负担线性可控。

**道理**：批量决策任务 / 拆成小 cycle 处理 / 决策者每次只看 8-10 项 / 5 分钟拍完。比"一次性扔大表格"高效 10×。

**可迁移**：

- 写公众号选题 / 不一次性想 30 个 / 一次想 5 个 / 跑一周看反响 / 再下一批
- 招聘面试 / 不积压 20 个简历同时筛 / 每天看 3-5 个 / 每天有判断
- 投资标的研究 / 不一次性 deep dive 10 家 / 一周一家 / 累积 10 周比拟"集中 10 周"质量更高（间隔让判断沉淀）

**深层原因**：人脑判断质量在"小批量 + 时间间隔"模式下远超"大批量 + 连续输入"。
